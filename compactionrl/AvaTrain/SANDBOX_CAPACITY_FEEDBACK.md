# Sandbox 并发容量问题反馈

CompactionRL 每个 rollout 会并发申请 64 个 Sandbox，其中 Primary 32 个、Secondary 32 个。

2026-08-25 04:16:01，客户端同时发起了 64 个创建请求。到第一个实例在 04:17:07 被销毁之前，共有 54 个不同的 Sandbox 实例返回 `HTTP 201` 并启动；其余约 10 个请求持续出现：

```text
HTTP 429
Sandbox capacity is exhausted
```

同时，Sandbox 平台创建接口本身还会返回：

```text
HTTP 500
Failed to create sandbox
```

该 `500` 是 `qz-sbx-api.sii.edu.cn/v1/sandboxes` 返回给 SDK 的 HTTP 状态，不是训练代码生成的错误。它与 `429` 同时出现，而且相同请求随后经重试可以成功，因此更符合平台容量或控制面瞬时失败，而不是请求参数或训练逻辑错误。

截至本次统计，整次运行的创建 API 尝试中记录到 `9639` 次 `201`、`3287` 次 `429` 和 `1211` 次 `500`。这些是请求尝试次数，不是失败 episode 数；绝大多数失败尝试随后重试成功，最终抛出 `500: Failed to create sandbox` 的 rollout 任务共记录到 36 次。最近一轮有 81 次 `429`、24 次 `500`，最终只有 1 个任务因创建失败退出并触发补采。

这里的 54 是同时存活实例数，不是累计次数：第一个 `DELETE` 发生前日志已有 54 个 `201` 和 54 个不同的 Sandbox 域名。剩余请求在 04:16:31 至 04:17:06 期间仍持续收到 `429`，最晚已经进入第 7 次重试。第一个实例释放后，等待中的请求才继续获得创建机会。

平台收到超出当前容量的请求后直接返回 `429`，没有服务端排队。当前由客户端执行指数退避重试：初始等待约 2 秒，单次最长约 30 秒，最多重试 120 次，并加入随机抖动。

因此，本次日志能直接证明：申请 64 个时，平台当时最多允许本任务同时成功运行 54 个，剩余约 10 个需要等待已有实例释放后再重试。54 是该时刻观测值，不足以单独证明平台存在固定的 54 硬配额，因为账户中其他任务或平台全局容量也可能占用资源。等待和补采导致 rollout 出现明显长尾并降低 GPU 利用率。

需要平台侧确认当前账户、项目或资源池的并发配额，并提供稳定的 64 并发容量。
